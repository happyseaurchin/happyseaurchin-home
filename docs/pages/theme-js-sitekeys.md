# `theme.js` siteKeys

the keys this device keeps, never in plain text (5 Nov 2026, the doors' battery §8 item 20; `spine:security-schematic` 1.12 and 4.3): every page that keeps a key asks `siteKeys.get/set/del` (and `ready()` before a read at load) under the names it always used, and the key is kept wrapped under a key the browser will not hand out (the beach's `button/seal.js` keep, a non-extractable AES-GCM key in this origin's IndexedDB), as the voice keeps its own. The five names the voice reads as keys (`next-latch:<block>`, `mirror-latch:<block>`, `passport-latch:<h>`, `lists-latch:<h>`, `now-latch:<h>`) move onto the voice's own `beach-key:<block>`, so page and voice keep one copy a block; every other name a key stood under (`here-latch:`, `journal-latch:`, `grain-latch:`, `shell-latch:`, `next-keeper:`, `morning-keeper:`, `invite-keeper:`, `models:key:`, `gallery:pass`, `gallery:key`, `gallery:place-key`, `group:narrator`) is wrapped where it stands; two old names holding different keys for one block leave the second as `beach-spare:<old name>` until a key is next given. Each plain copy is moved on load (the voice's names synchronously, before any voice reads, once the browser has wrapped a key: `site-keys:able`); a browser that cannot wrap keeps what it kept and is given nothing new. The voice's pass (`beach-pass:<beach>`) is a pass, not a key, and stays as the voice keeps it.
